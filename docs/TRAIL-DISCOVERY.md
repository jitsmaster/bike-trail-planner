# Live trail discovery: the "find trails near here" half of D23

Written 2026-09-16. **D23 final answer (a):** the app bundles a regional trail set
(`docs/REGIONAL-TRAILS.md`) **and** offers a live "find trails near here" button. This document
covers the live half only: the query, the mirrors, the freshness rule, what an answer becomes, how
it merges with the bundled trails, the cache, and what it does not promise.

Code:

| File | What it does |
|---|---|
| `data/OverpassClient.kt` | one query text in, one parsed JSON tree out; mirror rotation, freshness check, the query text itself (`DiscoveryQuery`) |
| `data/TrailDiscovery.kt` | Overpass answer -> `Trail` + `AccessPoint` (`DiscoveryParser`), the cache-aware `discover(...)`, and `DiscoveryMerge` |
| `data/DiscoveredTrailStore.kt` | the `discovered_trail` Room table, its DAO, the cache interface, the TTL/cap policy |
| `data/Room.kt` | registers the table and bumps the database to v3 |
| `app/src/test/java/com/biketrailplanner/TrailDiscoveryTest.kt` | the tests, including the live probe |

Nothing here is wired into the UI or the ViewModel yet: this is the data/domain layer plus its tests.

## 1. The query

Exact text, generated by `DiscoveryQuery.text(origin, radiusKm)` with the configured
`trail_radius_km` (5.0) and the live position. This is the text that was run against the live server
on 2026-09-16 (section 6), and its output is the recorded fixture:

```
[out:json][timeout:25];
(
  relation(around:5000,47.240371,-122.262019)["route"="bicycle"];
  relation(around:5000,47.240371,-122.262019)["route"="mtb"];
);
out geom;
```

POSTed to `/api/interpreter` as the form body `data=<urlencoded ql>`, with a User-Agent that
identifies the app. Notes, each of them measured or enforced by the code:

1. **Two statements, not a regex.** `route=bicycle` and `route=mtb` are asked for separately. This is
   the form that was verified against the live server; a single `["route"~"^(bicycle|mtb)$"]`
   statement was written but never used, so nothing here claims anything about it.
2. **`around:` takes metres.** The configured 5.0 km becomes `around:5000`.
3. **`out geom` returns the FULL geometry of every member way, inline.** A relation is *selected* by
   proximity, but returned whole. Measured: the 5 km search near home returned the **King County
   Interurban Trail at 83.59 km**, 530 points, because the relation passes within 5 km. That is why
   access points are capped by distance from the origin (section 3) - a naive client would hand the
   planner 280 entrances strung across 83 km of trail.
4. **`[timeout:25]` matches the client's per-attempt ceiling** (`OverpassClient.ATTEMPT_TIMEOUT_S`),
   so a stuck query cannot outlive the HTTP call.
5. **The query carries the rider's position** to a volunteer third-party server - the same class of
   leak as D12 (public router) and D21 (public basemap). Section 7 has the follow-ups this needs.
6. **The response must be dated.** `osm3s.timestamp_osm_base` is read from every response; see the
   freshness rule below.

## 2. Mirrors and the freshness rule

Mirrors, tried in this order:

1. `https://overpass-api.de/api/interpreter` (the reference instance)
2. `https://overpass.kumi.systems/api/interpreter`
3. `https://overpass.osm.ch/api/interpreter`

**Rule 1 - age.** `osm3s.timestamp_osm_base` is read from every response. A response whose OSM data
is older than **48 h** (`OverpassClient.STALE_AGE_MS`) is refused, the mirror is skipped and the next
one is tried. 48 h is the chosen number because the instances normally lag live OSM by
minutes-to-hours: two days behind means replication has stalled at that instance, while a shorter
window would throw away an instance that merely paused over a maintenance window. A response with
**no parseable stamp is refused as well** - an undated answer cannot prove its freshness, and the app
never presents undated data as current.

**Rule 2 - monotonicity.** A response whose stamp is older than the newest stamp **any** mirror has
already served in this process is refused even when it is inside the 48 h window. Having seen fresher
data already proves that instance is lagging.

**Rule 3 - an empty answer is not a verdict.** A response can be fresh, well-formed and carry **zero**
route relations. Repeating that to the rider as "no trails here" would be the worst wrong answer this
feature can give: a mirror with a thin or partial database would tell someone standing next to a trail
that there is none. So an empty answer is **second class**: the client records it as `EMPTY`, asks
**exactly one more mirror**, and only accepts "nothing here" when that mirror agrees as well
(`MAX_EMPTY_ATTEMPTS = 2` - two empty answers, never more). The reasoning for the bound is the quota
evidence in section 6: HTTP 429 arrives after three rapid queries, so the extra question is spent only
on the answer that would otherwise be silently wrong. The mirrors that said empty are recorded
(`OverpassAnswer.emptyMirrors`, `DiscoveryResult.emptyMirrors`) and the rider-facing summary names
them: *"no trails found within 5.0 km; confirmed by overpass-api.de and overpass.kumi.systems"*. If no
second mirror is left to ask, the answer is accepted but marked **unconfirmed**, and the summary says
so: *"only overpass-api.de answered, so another try may still find some"*.

Every attempt is recorded - the mirror, the `timestamp_osm_base` it served and whether it was accepted
or refused and why - and the record travels with the answer (`OverpassAnswer.attempts`,
`DiscoveryResult.attempts`), so the UI can say which mirror was skipped instead of guessing.

On a refusal the client rotates to the next mirror: at most one attempt per mirror, never more than
4 attempts in total, 25 s per attempt. HTTP errors, empty bodies and timeouts rotate in the same way.
If every mirror fails, `OverpassException` carries one line per mirror (`mirror -> STALE: ...`), and
**no exception message contains the query or the coordinates**. A User-Agent is mandatory: the public
instances answer HTTP 406 without one (measured against `overpass-api.de` with a library default UA).

### Why the freshness rule is not paranoia - measured evidence

* **This project already has the receipt.** `docs/SAFETY-PROBE.md` (section "stale mirror", and its
  findings list) records that `overpass.kumi.systems` answered **HTTP 200 with stale snapshots**,
  `timestamp_osm_base 2026-06-01T08:52:28Z` and `2026-07-28T02:16:18Z` against a current
  `2026-09-15T21:06:55Z`, and that the 2026-06-01 answer **silently truncated the White River Trail
  relation to 3 of its 5 member ways**. HTTP 200 is not evidence of anything.
* **2026-09-16, this work:** `overpass.osm.ch` answered HTTP 200 in 622 ms with an **empty element
  list** and a `timestamp_osm_base` of `117059` - not an instant at all - for exactly the query the
  reference mirror answers with 7 relations and 102,827 bytes. Recorded verbatim:
  `docs/discovery-raw/overpass-osm-ch-2026-09-16.json` (+ `.meta`). A client without the freshness
  rule would tell a rider standing next to the Interurban Trail that there are no trails here.
* **2026-09-16, this work:** `overpass.kumi.systems` did not answer at all (90 s and 150 s read
  timeouts, twice), and `overpass-api.de` answered HTTP 504 and HTTP 429 under repeated use (section 6).

## 3. What an answer becomes

`DiscoveryParser` turns the relation list into the app's own model. One relation -> one `Trail`:

* **Geometry.** Member ways are concatenated in relation order; a way that starts where the previous
  one ended shares that node, so the shared point is not repeated. Relation order is assumed to be the
  riding order and a gap between consecutive members is bridged by a straight segment - the app does
  not re-route a discovered trail.
* **Length.** `lengthM` and `rideableM` are both the geometry length. **No closure is known** for a
  discovered trail, so `closures = emptyList()`, `closedM = 0.0` and `rideableSpans` is the whole
  geometry.
* **`verified = false`.** Always. Nothing discovered has been closure-checked or surface-audited, and
  neither has the bundled regional set.
* **`paved = false`, `surface = emptyList()`, `untaggedSurfaceM = lengthM`.** The app has no surface
  audit here, so it may not claim one; every metre is honestly "not audited".
* **`loop`** is true only when the geometry really returns to its start (within 120 m). Measured: none
  of the 7 relations near home closes, so all 7 are out-and-back.
* **`nearestFromHomeM` / `farthestFromHomeM`** are measured from the *discovery origin* (the live
  position), not from the saved home.
* **Names.** `name`, else `"Unnamed bike route"`, else the `ref` is left alone. A name is the app's
  trail identity (`TrailNetwork.trail(name)`, corridors, joins), so a second trail may not reuse one:
  a colliding name gets `" (r<relationId>)"` appended. Never a silent rename, never one name for two
  corridors.
* **Noise filter.** A relation whose geometry is under 200 m, or which has fewer than two points, is
  dropped as a mapping fragment rather than offered as a ride.

**Access points** (`AccessPoint`), per discovered trail:

* the two **endpoints always**, plus interior points every ~300 m;
* capped at **12 per trail**, the interior slots filled by crow-flies distance from the origin,
  nearest first - so a long trail cannot flood the planner with entrances. Measured: every one of the
  six longer near-home relations reaches the 12, and only the short Interurban Trail Edgewood (1.33 km,
  which samples to 6 points in total) has fewer;
* `probeRouteKmFromHome = null`, `onRoad = null`, `highway = null`: the approach distance is
  **genuinely unknown**, and the planner MEASURES it live from the rider's position
  (`Planner.liveApproachM`, SPEC section 7 / D22). Nothing is invented;
* `sharesTrailNode = true` (the sampled point lies on the trail geometry);
* `osmNodeId` is **negative and synthetic**: `-(relationId * 100000 + sampleIndex)`. A sampled point
  is not an OSM node, and a negative id can never collide with a real node id, which is always
  positive. Callers must not present it as an OSM node.

Measured on the recorded near-home answer: **7 relations -> 7 trails, 78 access points**.

## 4. Merging with the bundled trails (discovery never replaces the bundle)

`discover(origin, radiusKm, forceRefresh, bundled)` takes the bundled trails the caller already has,
and `DiscoveryMerge` builds what the planner sees.

1. **A discovery a bundled trail already covers is left out, and reported.**
   `DiscoveryResult.coveredByBundled` lists it with the reason. The rule: **the same name**
   (case-insensitive, trimmed) **and at least 60% of the discovered geometry within 300 m of the
   bundled geometry** (`BUNDLED_COVERAGE` / `BUNDLED_NEAR_M`). Same name alone is not enough - two
   different corridors may share a name, and dropping one would silently delete a trail.
2. **A discovered trail whose name is already in use** (by a kept discovery or by a bundled trail)
   gets `" (r<relationId>)"`, so a merged network can never have one name pointing at two corridors,
   and a discovered name can never address a *verified* bundled trail.
3. **Duplicates inside one answer are collapsed, and reported.** Two relations are the same trail when
   either (a) their member-way id sets overlap by >= 0.8 (Jaccard), or (b) they share a name and >= 90%
   of the shorter geometry lies within 50 m of the longer. The longer geometry is kept. Reported in
   `DiscoveryResult.duplicatesCollapsed`.
4. **`DiscoveryMerge.network(bundled, discovered)`** returns the union: bundled trails, joins,
   corridors and road links untouched, discovered trails appended with `verified = false`.
   **`DiscoveryMerge.accessPoints(bundled, discovered)`** appends their access points.
5. **Measured near home:** with the bundled six handed in, **6 of the 7 relations are already covered**
   (the bundled near-home six *are* those relations) and **1 is kept: the King County Interurban Trail**
   (83.59 km, 12 access points). So the live button adds exactly the longer relation the bundle does not
   carry, and nothing else - and it adds it as unverified.

## 5. The cache

Table `discovered_trail` (Room v3):

| Column | Meaning |
|---|---|
| `bucket` (PK) | `RouteKey.bucket(origin)` - the same ~1 km cell the saved trips use |
| `origin_lat`, `origin_lon` | the position the answer was fetched for |
| `radius_km` | the search radius this answer covers |
| `payload` | the **raw Overpass JSON**, exactly as it arrived |
| `fetched_at` | when it was fetched |
| `timestamp_osm_base` | the mirror's OSM data stamp |
| `mirror` | which instance served it |

* **TTL 30 days** (`DiscoveryCachePolicy.TTL_MS`). A discovered trail needs no closure check to be
  useful, but it must not become a permanent claim about the world either: after a month the app asks
  again rather than showing a trail that may have been rerouted or closed since.
  **The TTL is a use-again rule, not a delete rule.** Rows are *not* swept by age; there is deliberately
  no delete-by-age query in the DAO. Deleting an expired row would delete exactly the answer the rider
  needs when the network is down (see the fallback below).
* **Cap 24 rows** (`DiscoveryCachePolicy.MAX_ROWS`), newest fetched first, enforced on every write.
  This cap is the one thing that bounds the table. The shipped 5 km answer measured **102,827 bytes**,
  so 24 rows come to about **2.5 MB**. For scale, a 25 km search measured **1,181,984 bytes /
  38 relations** - which is exactly why a cap exists instead of "keep everything".
* **One indexed lookup.** The read is `SELECT * FROM discovered_trail WHERE bucket = :bucket`, a
  primary-key probe. No full-table scan; the TTL sweep and the trim are the only set operations and
  they run on write.
* **`discover(origin, radiusKm, forceRefresh = false)`** returns the cached answer without touching the
  network when the bucket has a row that is inside the TTL **and was searched at least as wide** (a
  5 km row does not answer a 20 km request). `forceRefresh = true` skips the cache and writes the new
  answer back. A row that no longer parses is ignored and re-fetched rather than failing the plan.
* **Stale cache beats no answer.** When *every* mirror fails (all refused, all unreachable), the app
  does not fail while it still holds an answer for that bucket: it returns the cached one - **even past
  the 30-day TTL** - with `fromStaleCache = true`, the age (`fetchedAgeMs`), the mirror that served it
  and `staleReason` (the per-mirror failure list). The rider-facing summary says plainly *"Overpass could
  not be reached (`overpass-api.de -> FAILED: IOException; ...`), so this is the cached answer, from
  overpass-api.de, OpenStreetMap data of ..., fetched 41 days ago, which may be out of date"*. The one
  guard that still applies is the radius: a cached 1 km answer is **not** used for a 5 km search, even
  as a fallback, because under-reporting is the same wrong answer this whole section exists to prevent.
  Only when there is no cached row at all - or it cannot be parsed - does discovery fail with the
  per-mirror reasons.
* The cache stores the raw JSON, so a change to `DiscoveryParser` applies to cached answers too - the
  table cannot drift from the parser.
* An empty answer that two mirrors confirmed is cached like any other answer, so a repeat plan in a
  genuinely trail-free area costs nothing either. A cached empty answer reports `emptyConfirmed = true`
  (its mirrors are not kept with the row, so the summary says "the cached answer found none" instead of
  naming them).
* Room is bumped to **version 3** with `fallbackToDestructiveMigration()`: the table is a cache of
  something the app can always fetch again, so dropping it on upgrade is safe and no migration is
  needed (the same reasoning as v2's `saved_route`).

## 6. Measured numbers (live smoke probe)

Run with the real mirrors and the real home position:

```
export JAVA_HOME=/opt/homebrew/opt/openjdk@17
./gradlew :app:testDebugUnitTest --tests 'com.biketrailplanner.TrailDiscoveryTest'
```

The probe writes `app/build/live-discovery-probe.txt` and skips itself (JUnit `Assume`) when Overpass
cannot be reached, the way `LivePlanProbeTest` skips when Valhalla is down. Runs on 2026-09-16:

| | 18:39 | 18:41 | 18:46 (repeat, warm) |
|---|---|---|---|
| mirror that served it | `overpass-api.de` | `overpass-api.de` | `overpass-api.de` |
| round trip (query + parse + merge) | 10,757 ms | 9,983 ms | **1,397 ms** |
| of which the accepted mirror | - | 9,976 ms | **1,393 ms** |
| `timestamp_osm_base` | 18:39:05Z | 18:41:05Z | 18:46:12Z |
| data age when fetched | ~2 min | ~2 min | ~2 min |
| raw answer | 102,827 bytes | 102,827 bytes | 102,827 bytes |
| route relations in the answer | 7 | 7 | 7 |
| trails kept after the bundled merge | 1 | 1 | 1 |
| access points | 12 | 12 | 12 |
| covered by a bundled trail | 6 | 6 | 6 |
| `mtb` relations found near home | 0 | 0 | 0 |

The kept trail was the **King County Interurban Trail (r1900725): 83.59 km, 530 points, loop=false**,
with 12 access points.

The same query measured outside the app (curl/requests, same User-Agent, same body) explains the
timing, and is the honest reason the probe reports ~10 s rather than ~1 s:

| attempt | result | time |
|---|---|---|
| first after an idle period | HTTP 200, 102,827 bytes, 7 relations | **10,571 ms** |
| same query 3 s later | HTTP 200, identical payload and stamp (mirror-side cache) | **1,025 ms** |
| third, 3 s after that | **HTTP 429** (rate limited) | 10,928 ms |

So: the first call after an idle period costs about ten seconds, a repeat within a few minutes is
1.0-4.1 s (the instance caches its own answer), and a third request seconds after the second is refused
with HTTP 429 - which the client handles by rotating to the next mirror. The probe's runs on 2026-09-16
measured 10,757, 9,983, 4,137, 2,620 and 1,397 ms, **every one returning the identical 102,827-byte
payload**: the spread is the mirror's load and its own cache, not the app's work. The **button must therefore show progress**, and the app must not fire the query twice in
a row: the location-bucket cache is what makes a repeat plan free.

| File | What it is |
|---|---|
| `docs/discovery-raw/overpass-near-home-5km.json` | the real 5 km answer for the home position: 7 relations, 102,827 bytes, stamp 2026-09-16T18:33:04Z (fetched in 1,946 ms) |
| `...json.meta` | mirror, bytes, HTTP time, elements, stamp, and the exact query text |

The near-home fixture is what the parsing tests assert against, so the tests describe what the public
instances actually return.

## 7. What this does NOT promise

1. **No closure verification.** A discovered trail may be closed, washed out or built over. The
   Sumner Link closure is known because it was measured (SPEC section 7b); nothing here has been.
2. **No surface audit.** `paved = false` and every metre is "not audited". A trail tagged asphalt may
   be gravel.
3. **No measured traffic.** `assets/traffic.json` and `assets/limits.json` cover Pierce County and the
   WSDOT state highways. Away from home they match almost nothing, so **most roads grade UNGRADED and
   the safety grade is advisory, not a promise.** The UI must keep saying so.
4. **No access-point measurement.** `probeRouteKmFromHome` is null on purpose; the approach is measured
   live by the planner, and if that measurement fails the planner falls back to crow-flies, which is
   the proxy D24 disproved.
5. **No elevation, difficulty or MTB grading.** A `route=mtb` relation is not rated here.
6. **No offline support, and a new third-party dependency.** Planning a discovered trail needs a
   network connection to a volunteer instance, and depends on that instance being up. When all three
   mirrors are down or stale the app falls back to the cached answer for that area, aged and labelled
   (section 5); a discovered trail is therefore only *fresh* with a working connection. If there is no
   cached answer either, discovery fails with a per-mirror reason and the app must say "discovery
   unavailable" rather than "no trails here".
7. **Data currency is the mirror's, up to 48 h.** The stamp is shown to the rider instead of being
   hidden.
8. **The rider's position leaves the phone** (the query carries it). Same class as D12 and D21.
   **Follow-ups D23 asks for and this work does not include:** an entry in `docs/SECURITY.md`
   (third-party dependency, position leak) and in `docs/DATA-LICENSES.md` (ODbL; "© OpenStreetMap
   contributors" is already displayed).
9. **Nothing is wired into the UI or the ViewModel yet.** This is the data/domain layer, its tests and
   this document.

## 8. Tests

`app/src/test/java/com/biketrailplanner/TrailDiscoveryTest.kt` (24 tests):

* the query text: statements, radius in metres, `out geom`;
* **the recorded answer** -> 7 trails with the real names, 530 geometry points and 83.59 km for the
  King County Interurban Trail, `verified = false`, no closures, no surface claim, `rideableM` =
  geometry length for all of them;
* **access points**: both endpoints always (including a 20 km synthetic trail whose far endpoint a
  "nearest twelve" rule would have dropped), the 12 cap, ~300 m interior spacing, negative unique
  synthetic ids, nearest-first order, `probeRouteKmFromHome == null`;
* **duplicate collapse**: an injected repeat of the recorded Sumner Link relation is collapsed and
  reported; a same-named relation on the same corridor is collapsed, the same name on a different
  corridor is not, and it is renamed with its relation id;
* **mirror rotation**: a six-day-old first mirror is refused and the fresh second mirror wins, with the
  stale mirror reported; a mirror older than what another already served is refused inside the age
  window; the recorded broken `overpass.osm.ch` body is refused for not being an instant; a total
  failure lists the mirrors and **never** contains the coordinates;
* **the cache**: a second call for the same bucket makes no network call (call counting), `forceRefresh`
  does, a different bucket does, a row past the TTL does not answer, a 5 km row does not answer a 20 km
  request, and 81 writes leave exactly the cap;
* **an empty answer is not a verdict**: an empty first mirror is seconded by the next one, whose data is
  what the app uses; two empty mirrors confirm "nothing here" (and the summary names both); a
  single-mirror empty answer is reported as one mirror's word, not a verdict;
* **stale cache beats no answer**: with every mirror failing and an expired row present, the cached
  answer comes back with `fromStaleCache = true` and its age (40 days), the failure reasons, and a
  summary that says Overpass could not be reached; with no row at all, or only a row too narrow for the
  search, the failure is reported instead;
* **merging**: a covered relation is reported and left out, an uncovered one is added with
  `verified = false`, the bundled six keep their own flags, and the summary line names the mirror and
  the data stamp;
* **the live smoke probe**, gated by an `Assume` on Overpass reachability, whose output is
  `app/build/live-discovery-probe.txt`.
